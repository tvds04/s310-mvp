DESCRIPTION:
As a participant, I want to submit a project document draft so that my team's Technology Consultant (TC) can review our progress and provide actionable guidance.

ACCEPTANCE CRITERIA:
1. The system shall provide a secure portal for the participant to upload document files representing their project draft.
2. The system shall restrict file uploads to standard document formats (e.g., .pdf, .docx) and enforce a maximum file size limit.
3. The system shall automatically associate the uploaded project draft with the participant's specific ProjectID and generate a unique DocumentID.

7. The system shall allow the participant to view their previously submitted drafts but restrict them from deleting or overwriting a draft once it has been submitted.

SCRUM-8 | Accept/Reject Project (pic)
--------------------------------------------------------------
Status: TO DO
Priority: Medium
Assignee: Christopher Dvorak
Reporter: Jason Tang
Sprint: None
Story Point Estimate: None
Parent: None
Labels: None
Due Date: None

DESCRIPTION:
As an MC member, I want to review submitted project applications and record my accept or reject decision, so that I can ensure only feasible, well-scoped projects are included in Project Future.

ACCEPTANCE CRITERIA:
1. The system shall display a list of all submitted project applications, each showing the client name, organization type, project name, and current status (pending, accepted, rejected).
2. The MC member shall be able to open a project record and view all project details, including client information and interview notes recorded by the MC member who conducted the interview.
3. The system shall require that interview notes are present on a project record before an accept/reject decision can be submitted (a decision cannot be made without an interview assessment).
4. The MC member shall be able to select either "Accept" or "Reject" for each project and confirm the decision before it is saved.
5. Upon rejection, the system shall automatically send a polite notification message to the client thanking them for their application and explaining that only a limited number of projects can be accepted.
6. Upon acceptance, the system shall automatically send the client an email containing a legal authorization document as an attachment, granting student consultants permission to work on their project.
7. The authorization document notification shall inform the client that they have a two-week window to sign and return the document via the system.
8. The system shall provide a way for the client to upload and submit the signed authorization document.
9. Once a decision is recorded, the project status shall update accordingly (accepted or rejected) and the decision shall not be reversible without administrator (super-user) intervention.
10. The MC member shall only be able to act on projects assigned to their review queue; they shall not be able to alter another MC member's decisions.

Labels: None

DESCRIPTION:
As an MC member, I want to review student and alum applicants and record an accept or reject decision for each, so that I can assemble appropriately sized teams that match the number and scope of accepted projects.

ACCEPTANCE CRITERIA:
1. The system shall display a list of all student applicants, each showing the applicant's name, class standing, major, and application status (pending, accepted, rejected).
2. The MC member shall be able to open an individual applicant record and view all submitted application materials, including the applicant's resume, application letter, and any other submitted details.
3. The MC member shall be able to select either "Accept" or "Reject" for each applicant and confirm the decision before it is saved.
4. Upon acceptance, the system shall automatically send the applicant a notification confirming they have been selected to participate in Project Future.
5. Upon rejection, the system shall automatically send the applicant a respectful notification thanking them for volunteering and explaining that participation is limited.
6. The system shall display a running count of accepted applicants and accepted projects at all times during the review process, so the MC can make informed allocation decisions without exceeding team capacity.
7. The system shall allow the MC to accept a slightly larger pool of applicants than strictly needed, to account for potential dropouts (no hard cap is enforced by the system).
8. The system shall flag applicants whose interview notes have been recorded (for cases where a client interview was also associated with an applicant record) so the MC has full context.
9. Once a decision is recorded, the applicant's status shall update in the system immediately and the decision shall not be reversible without administrator (super-user) intervention.
10. The system shall ensure that rejected applicants are not visible in the team formation workflow, so that only accepted participants are eligible to be assigned to project teams.

SCRUM-16 | Submit Final Documents and Request Eval
--------------------------------------------------------------
Status: TO DO
Priority: Medium
Assignee: Christopher Dvorak
Reporter: Adhvika Venkatesh
Sprint: None
Story Point Estimate: None
Parent: None
Labels: None
Due Date: None

DESCRIPTION:
As a project team participant, I want to submit the final versions of my project deliverables and formally request client evaluation, so that the project can be officially closed and the client can provide their assessment of our work.

ACCEPTANCE CRITERIA:
1. The system shall allow a participant to upload and submit the final versions of all three required deliverables: the project charter, the final report, and the final presentation.
2. Final document submission shall only be available after the TC has reviewed and provided feedback on the draft version of each respective document.
3. The system shall require all three final documents to be uploaded before the "Request Evaluation" action can be triggered — partial submissions shall not initiate the evaluation process.
4. Upon submission of all final documents, the system shall automatically notify the client that the project is complete and prompt them to submit their evaluation via the system.
5. The client evaluation form shall include both structured rating questions (covering multiple dimensions of the experience) and an open-ended comments field.
6. The system shall automatically send a copy of the completed client feedback to the project team members once the client submits their evaluation, supporting it as a learning outcome.
7. The TC shall not receive a copy of the final document submissions (only draft submissions trigger TC notification per system rules).
8. The project status shall update to "Complete" once the client feedback has been submitted, closing out the project record.
9. The system shall notify the TC that a final version has been submitted (without attaching a copy), so the TC is aware the project has moved to closure.
10. A super-user (Bikar / administrator) shall be able to view all submitted final documents and client evaluations at any time for oversight and program assessment purposes.
